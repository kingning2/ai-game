# Rust 测试代码组织规范

编写、修改 Rust 代码时，必须遵守以下测试规范。

## 1. 测试与业务代码分离

- 默认不要在业务 `.rs` 文件末尾追加 `#[cfg(test)] mod tests`。
- 优先将测试代码放在独立的测试文件中。
- 不要为了给每个 `.rs` 文件配套测试而机械地创建测试文件。
- 测试应围绕模块职责和业务行为组织，而不是按照源文件数量组织。

## 2. 测试目录结构

优先采用以下组织方式：

```text
src/
├── lib.rs
├── config/
│   ├── mod.rs
│   ├── loader.rs
│   ├── parser.rs
│   └── tests.rs
├── agent/
│   ├── mod.rs
│   ├── runtime.rs
│   ├── executor.rs
│   └── tests.rs
└── error/
    └── mod.rs

tests/
├── config_integration.rs
├── agent_integration.rs
└── fixtures/
```

具体要求：

- 模块内部单元测试：优先放在对应模块的独立 `tests.rs`。
- 跨模块集成测试：放在 crate 根目录的 `tests/`。
- 测试数据、模拟文件和固定输入：统一放在 `tests/fixtures/` 或模块专属测试目录。
- 不要把多个无关模块的测试全部堆积到一个文件中。

## 3. 私有函数测试

如果测试需要访问模块内部的私有函数、私有字段或内部实现：

- 可以在对应模块声明独立测试子模块。
- 优先使用 `#[cfg(test)]` 配合 `#[path = "..."] mod tests;`。
- 不要为了测试而将原本私有的函数、字段改成 `pub`。
- 不要为了测试方便而扩大生产代码的公开 API。

示例：

```rust
// parser.rs

pub fn parse_config(input: &str) -> Result<Config, Error> {
    // implementation
}

#[cfg(test)]
#[path = "parser/tests.rs"]
mod tests;
```

## 4. 测试质量要求

- 测试必须验证实际业务行为，不能只为了提高测试数量而编写无意义测试。
- 优先覆盖正常流程、边界条件、异常输入和错误处理。
- 对异步函数使用适当的 Tokio 测试支持（`#[tokio::test]`）。
- 对数据库、文件系统、网络等外部依赖，优先使用隔离的测试环境、Fixture 或 Mock。
- 不要在单元测试中依赖真实生产环境、生产数据库或外部服务。
- 测试应具备可重复性，避免依赖执行顺序和不稳定的外部状态。

## 5. 修改代码时的要求

- 修改业务逻辑时，检查现有测试是否需要同步更新。
- 新增重要业务逻辑时，必须评估是否需要新增测试。
- 修复 Bug 时，优先增加能够复现该 Bug 的回归测试。
- 不要删除或弱化现有测试来规避失败。
- 不要为了让测试通过而修改与问题无关的业务逻辑。

## 6. 执行与交付要求

完成代码修改后：

1. 运行对应模块的测试。
2. 运行 `cargo test`，确保相关测试通过。
3. 条件允许时运行 `cargo fmt --check` 和 `cargo clippy`。
4. 如果测试无法运行，明确说明原因。
5. 最终说明新增或修改了哪些测试，以及实际执行的测试命令和结果。

## 7. 核心原则

测试代码默认与业务实现分离。

优先采用清晰、可维护的独立测试模块；只有在需要访问私有实现且独立测试模块不适合时，才考虑内联测试。

不要为了测试而过度设计目录结构，也不要为了追求测试覆盖率而编写无实际价值的测试。
